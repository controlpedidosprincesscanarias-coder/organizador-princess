# ✨ Organizador Princess v4.18.40

## 🔧 Se vuelve a abrir bien después de actualizar

- Con la 4.18.38, al terminar «Actualizar ahora» el Organizador nuevo podía no abrirse: «Failed to load Python DLL …\_MEI…\python312.dll». La instalación sí se había hecho; fallaba solo la reapertura automática.
- **Causa:** el instalador heredaba del Organizador viejo las variables internas de PyInstaller (`_PYI_*`) y se las pasaba al nuevo, que buscaba Python en la carpeta temporal del viejo. Antes de la 4.18.38 esa carpeta seguía ahí porque el viejo se cerraba a la fuerza; desde que se cierra normalmente, se borra.
- **Arreglo:** el instalador abre el Organizador nuevo sin esas variables y con `PYINSTALLER_RESET_ENVIRONMENT=1`, lo que también arregla la actualización desde la 4.18.38. Además, el Organizador las quita antes de lanzar el instalador.

# ✨ Organizador Princess v4.8.0

## 🚀 Novedades principales

Corrige el propio script de comprobación de dependencias añadido en v4.8.0:
`socketio.__version__` no existe en la versión instalada de python-socketio,
así que el chequeo previo a compilar fallaba con un `AttributeError` aunque
las dependencias estuvieran perfectamente instaladas. Ahora el chequeo solo
confirma que cada módulo se puede importar, sin depender de atributos de
versión que varían entre paquetes.

Si en v4.8.0 el .exe daba `ModuleNotFoundError: No module named 'requests'`
pese a tener las dependencias instaladas, la causa más probable seguía
siendo la de v4.8.1: un `pyinstaller.exe` en el PATH resolviéndose a un
Python distinto al que tiene las dependencias — por eso `compilar.bat`
sigue usando `python -m PyInstaller` en vez de `pyinstaller` a secas.

Chat interno entre compañeros: botón "💬 Chat" en la Agenda. Reutiliza tu
mismo usuario y contraseña de Control de Pedidos (el mismo que ya usa el
bridge de avisos) — sin login nuevo. Conversación general con todos, o
privada 1 a 1. Entrega en tiempo real cuando la conexión lo permite; si no,
cae sola a modo más lento sin perder mensajes.

Requiere backend `control_pedidos` v12.6.0 o superior.

Parche de compilación: corrige el error `ModuleNotFoundError: No module
named 'requests'` al ejecutar el .exe compilado de la v4.8.0 (el chat
funcionaba en `python main_agenda.py` pero no en el ejecutable). La causa
más probable es que `pyinstaller` se estuviera resolviendo a un Python
distinto al que tenía instaladas las dependencias del chat.

`compilar.bat` ahora comprueba, antes de compilar, que `requests`,
`python-socketio`, `python-engineio` y `websocket-client` están instalados
en el mismo Python que va a usar PyInstaller (y para el propio
PyInstaller usa `python -m PyInstaller` en vez de `pyinstaller`, para
garantizar que es el mismo intérprete). También limpia la caché global de
PyInstaller (`%LOCALAPPDATA%\pyinstaller`), no solo la del proyecto.

Si ves el aviso de dependencias faltantes al compilar, ejecuta primero:
```
python -m pip install requests "python-socketio[client]" websocket-client
```

## 🔧 Corrección posterior (2026-07-20): instancias duplicadas y ventanas en blanco

Corregido un fallo por el cual, en algunos equipos, podían quedar dos
instancias de la aplicación abiertas a la vez sin que el usuario lo
notara — algo que provocaba avisos duplicados y ventanas emergentes en
blanco ("ventanitas ciegas") apiladas sobre la pantalla, incluso después
de cerrar la ventana visible.

La causa: el control de instancia única comprobaba y sustituía la
instancia anterior mediante un fichero con su PID, lo que dejaba una
pequeña ventana de tiempo en la que dos arranques casi simultáneos
podían "colarse" a la vez sin que ninguno detectara al otro. Ahora se
usa un mutex del propio sistema operativo, que Windows resuelve de
forma atómica: ya no es posible que dos instancias convivan por mala
suerte de tiempos, sea cual sea el momento exacto en que se abran.

De forma relacionada, se ha desactivado el cierre automático diario de
las 17:00 (seguía activo desde la v4.6.6/v4.6.8): ya no era necesario
como salvaguarda ahora que las instancias duplicadas están resueltas de
raíz, y no había ningún otro motivo técnico documentado que lo
justificara (`agenda.json` / `config.json` / `usuarios.db` son locales
por usuario, no un recurso compartido en red). Quien quiera dejar la
aplicación abierta todo el día puede hacerlo sin problema.

# ✨ Organizador Princess v4.7.0

## 🚀 Novedades principales

Esta versión permite configurar, desde Control de Pedidos, cada cuántas horas se repite el aviso emergente de un pedido en alerta — con un intervalo distinto según el tipo de pedido y su nivel (🔴 urgente / 🟡 aviso), o desactivar la repetición por completo para un tipo concreto. También corrige dos fallos: uno que impedía que los popups reflejaran los umbrales configurados en Admin, y otro que impedía que el aviso se repitiera correctamente al escalar de nivel.

---

## 🔧 Correcciones

### ⏱️ Los umbrales de Admin no se aplicaban a los popups de Agenda

Corregido un fallo por el cual cambiar los días de aviso/urgente de un tipo de pedido en Admin → Config Alertas solo afectaba a los avisos de email y Telegram del resumen diario, pero no a los popups que aparecen en Agenda mientras trabajas — que seguían usando un umbral fijo, sin relación con lo configurado. Ahora los tres canales (popup, email, Telegram) usan siempre el mismo umbral configurado en Admin.

### 🔁 El aviso no se repetía al escalar de "aviso" a "urgente"

Corregido un fallo por el cual, cuando un pedido pasaba de nivel 🟡 aviso a 🔴 urgente, el temporizador de repetición del popup no se reiniciaba como debía — así que podía tardar mucho más de lo esperado en volver a avisar tras el cambio de nivel.

---

## ⚡ Mejoras

### 🔁 Repetición de popups configurable por tipo de alerta

Ahora, desde Control de Pedidos → Admin → Config Alertas, se puede configurar para cada tipo de pedido (Enviado al proveedor, Firma Compras, Firma Hotel, Entrega Parcial, Cotización):

- Si el popup se repite o se muestra una única vez.
- Cada cuántas horas se repite si el pedido está en 🔴 urgente.
- Cada cuántas horas se repite si está en 🟡 aviso.

Si no se ha configurado nada para un tipo concreto, la aplicación sigue usando los intervalos de siempre, sin cambios de comportamiento.

# ✨ Organizador Princess v4.6.4

## 🚀 Novedades principales

Esta versión no cambia nada en el uso diario de la aplicación: corrige la causa por la que los avisos de Telegram de Control de Pedidos no llegaban a mostrarse como popup en pantalla, y añade capacidad de diagnóstico al sistema de notificaciones en segundo plano (bridge), que hasta ahora no dejaba ningún rastro en disco cuando algo fallaba internamente.

---

## 🔧 Correcciones

### 🔔 Popups de Control de Pedidos no se mostraban en pantalla

Corregido el fallo raíz por el cual las notificaciones de Control de Pedidos (Telegram) se recibían y confirmaban correctamente en segundo plano, pero **nunca llegaban a mostrarse como aviso emergente**.

La causa: el sistema de notificaciones intentaba localizar la función que dibuja el popup buscándola por el nombre del programa principal. Ese nombre no está disponible cuando la aplicación se ejecuta como programa (tanto en modo desarrollo como compilada), así que la búsqueda fallaba siempre de forma silenciosa, sin ningún error visible para el usuario — el aviso quedaba registrado como "recibido" pero jamás se llegaba a dibujar en pantalla.

Ahora la aplicación principal le entrega esa función directamente al sistema de notificaciones al arrancar, sin depender de esa búsqueda por nombre. Con esto se restablece la recepción de popups en tiempo real para todos los usuarios.

### 🩺 Diagnóstico del sistema de notificaciones (bridge)

Corregido un fallo por el cual el sistema de notificaciones en segundo plano no registraba su actividad en ningún archivo de log durante el funcionamiento normal de la aplicación. El registro únicamente se generaba al ejecutar el módulo de forma manual con fines de prueba, nunca durante el uso real de Organizador Princess.

En la práctica, esto hacía imposible comprobar si una alerta de Telegram enviada desde Control de Pedidos había llegado a intentar mostrarse como aviso emergente en pantalla, o si el fallo estaba en otro punto de la cadena — y fue precisamente este registro el que permitió encontrar la causa del fallo anterior.

Ahora toda la actividad del sistema de notificaciones — sincronizaciones periódicas, notificaciones push recibidas y cualquier error interno — queda registrada en:

```
%APPDATA%\OrganizadorPrincess\pedidos_bridge.log
```

---

## 🔔 Resultado

Se restablece la recepción fiable de popups en tiempo real para los avisos de Control de Pedidos, y queda disponible un registro de diagnóstico permanente para detectar con precisión cualquier fallo futuro en esta vía de notificaciones.
